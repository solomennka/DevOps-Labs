# Учебный сервис: Flask + PostgreSQL + nginx

Проект рассчитан на Windows 10/11, Docker Desktop и Git Bash или терминал VS Code. Пароль `dev_password_123` учебный: не используйте его для реальных данных.

## Что где находится

- `frontend/` — HTML-страница, которую в Лабе 0 отдаёт Flask, а в Лабе 1 напрямую отдаёт nginx.
- `app.py` — бэкенд: принимает HTTP-запросы, выполняет SQL-запросы и возвращает JSON.
- `db` из `compose.yaml` — отдельный сервер PostgreSQL. Данные хранятся в Docker volume `postgres_data`.
- `nginx/nginx.conf` — HTTPS, редирект, два backend-инстанса, ограничение запросов, `alias`, виртуальные хосты, 404 и Basic Auth.
- `backend1` и `backend2` — два одинаковых экземпляра Python-приложения с разными `INSTANCE_ID`.

## Лаба 0 — запустить локально

### 1. Установите инструменты

1. Установите Docker Desktop и дождитесь статуса, что Docker запущен.
2. Установите Python 3.12.
3. Откройте папку проекта в VS Code. Команды ниже рассчитаны на терминал **Git Bash**; если в VS Code открыт PowerShell, переключите профиль терминала на Git Bash.

Проверьте:

```bash
docker --version
docker compose version
python --version
```

### 2. Запустите только PostgreSQL

Из корня этой папки выполните:

```bash
docker compose up -d db
docker compose ps
```

Дождитесь, чтобы сервис `db` стал `healthy`:

```bash
docker compose ps
```

PostgreSQL — отдельная программа-сервер. Веб-приложение подключится к нему по адресу `localhost:5432`. Docker volume сохраняет данные независимо от остановки контейнера.

### 3. Создайте виртуальное окружение Python

```bash
python -m venv .venv
source .venv/Scripts/activate
python -m pip install --upgrade pip
pip install -r requirements.txt
```

Если последняя команда `source ...` не подходит вашему терминалу, используйте Git Bash в VS Code. После активации в начале строки терминала обычно появляется `(.venv)`.

### 4. Запустите бэкенд

```bash
export DB_HOST=localhost
export DB_PORT=5432
export DB_NAME=notesdb
export DB_USER=appuser
export DB_PASSWORD=dev_password_123
export INSTANCE_ID=local
python app.py
```

Оставьте этот терминал открытым. При первом запуске приложение создаёт таблицу `notes` в PostgreSQL. Откройте `http://127.0.0.1:5000` в браузере.

### 5. Проверьте, что данные действительно сохраняются

1. Добавьте заметку через форму.
2. Перезагрузите страницу — заметка должна остаться.
3. Можно остановить Python (`Ctrl+C`) и запустить `python app.py` снова — заметка тоже должна остаться.

Почему: заметка записывается SQL-командой `INSERT` в PostgreSQL. Она не хранится в HTML и не исчезает при перезагрузке вкладки.

### 6. Остановить сервисы

Остановить Python можно через `Ctrl+C`, затем остановить базу:

```bash
docker compose stop db
```

Не используйте `docker compose down -v`, если хотите сохранить учебные данные: ключ `-v` удаляет том базы данных.

## Лаба 1 — nginx

### 1. Подготовьте сертификат

В Git Bash из корня проекта:

```bash
bash generate-cert-gitbash.sh
```

Скрипт создаст самоподписанный сертификат для `app.local.test`, `other.local.test` и `localhost`. Браузер может предупреждать, что сертификат не является доверенным — для локального учебного стенда это ожидаемо. В `curl` используйте `-k`, чтобы разрешить самоподписанный сертификат.

### 2. Привяжите локальные домены

Откройте Блокнот **от имени администратора** и файл:

`C:\Windows\System32\drivers\etc\hosts`

Добавьте строки:

```text
127.0.0.1 app.local.test
127.0.0.1 other.local.test
```

Сохраните файл. Это не покупает домен и не меняет DNS в интернете: только ваш компьютер будет направлять эти имена на себя.

### 3. Создайте пароль для `/admin`

В Git Bash:

```bash
docker run --rm httpd:2.4-alpine htpasswd -nbB admin 'ChangeThisLocalPassword'
```

Команда выведет строку, начинающуюся с `admin:`. Скопируйте **всю строку** в новый файл `nginx/htpasswd` (без дополнительных строк). Не используйте настоящий пароль от какой-либо учётной записи. Файл `nginx/htpasswd` исключён из Git.

### 4. Проверьте файлы и поднимите весь стенд

Убедитесь, что существуют `certs/local.crt`, `certs/local.key` и `nginx/htpasswd`. Затем:

```bash
docker compose --profile lab1 up -d --build
docker compose ps
```

Откройте `https://app.local.test`. Это тот же фронтенд, но теперь его отдаёт nginx. `https://other.local.test` должен показывать другой статический сайт.

### 5. Как устроен запрос

1. Браузер запрашивает `https://app.local.test` и подключается к nginx на порту 443.
2. nginx по `root` читает статические файлы из `frontend/` и отдаёт HTML сам.
3. Страница вызывает `fetch('/api/notes')`. nginx направляет `/api/...` через `upstream backend_pool` одному из контейнеров `backend1` или `backend2`.
4. Бэкенд обращается к PostgreSQL по внутреннему имени Docker-сервиса `db`.
5. JSON возвращается назад через nginx в браузер.

Порты `backend1` и `backend2` не опубликованы на компьютере: к ним обращается nginx внутри Docker-сети. PostgreSQL при этом доступен с компьютера на `localhost:5432` для Лабы 0.

### 6. Проверки

Запустите из Git Bash:

```bash
bash check.sh
```

Ожидаемые признаки:

- HTTP возвращает `301` и заголовок `Location: https://...`.
- `/api/health` возвращает JSON с `"instance":"backend-1"` и `"instance":"backend-2"` в разных запросах.
- `/admin` без логина и пароля возвращает `401`.
- `/docs/` возвращает `200` и отдельную страницу.
- несуществующая страница возвращает `404` с текстом из `frontend/404.html`.
- `other.local.test` показывает второй сайт, а неизвестный HTTPS-домен получает `404`, а не главный сайт.
- при серии быстрых запросов к API появляются `429 Too Many Requests`.

Заголовок `instance` — учебный маркер, который показывает, какой именно backend ответил. Если несколько запросов подряд вернулись с одного инстанса, это не обязательно ошибка: запросы могут попасться в одном порядке. Повторите проверки медленно.

### 7. Проверка отказоустойчивости — самое важное

```bash
docker compose stop backend1
curl -k https://app.local.test/api/health
docker compose start backend1
```

Пока `backend1` остановлен, API должен продолжать отвечать от `backend2`. nginx узнаёт о недоступном сервере по ошибкам подключения и временно перестаёт направлять на него запросы. После запуска `backend1` он снова может участвовать в балансировке. Для отчёта сохраните вывод команд и скриншот `docker compose ps` до и после остановки контейнера.

### Полезные команды

```bash
docker compose logs -f nginx       # логи nginx
docker compose logs -f backend1   # логи первого бэкенда
docker compose logs -f backend2   # логи второго бэкенда
docker compose ps                 # состояние контейнеров
docker compose --profile lab1 down # остановить и удалить контейнеры, том БД сохранится
```

## Что приложить в отчёт

**Лаба 0:** ссылка на Git-репозиторий, README с запуском, скрин страницы с сохранённой заметкой после обновления.

**Лаба 1:** `nginx/nginx.conf`, `check.sh`, скриншоты конфигурации и работающей страницы, вывод проверок редиректа, двух `instance`, остановки одного бэкенда, `401`, `429`, отдельного виртуального хоста и `404`.

## О звёздочке (проверка уязвимостей)

Проверяйте path traversal, перебор путей и другие ошибки только на своём стенде, специально созданной учебной цели или системе, на тестирование которой у вас есть явное разрешение. Не запускайте перебор и проверки на случайных публичных сайтах. В отчёте запишите точный URL своей лабораторной цели, тест, результат и как конфигурация была исправлена.
